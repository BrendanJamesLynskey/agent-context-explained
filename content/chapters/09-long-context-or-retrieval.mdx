<Layer kind="concept">

Context windows of a million tokens raise an obvious question: why retrieve at all? Put the whole document set in the prompt and let the model find the answer. The engine prices that against retrieval, question by question, from the engine's dated list prices and cache rules (the same accounting as [Agent Harnesses Explained, prompt caching](https://agent-harnesses-explained.vercel.app/learn/04-prompt-caching)) and token counts measured on this corpus: a system prompt of <V of="tradeoff.sizes.system" fmt="int" /> tokens, questions of <V of="tradeoff.sizes.question" fmt="num" /> tokens on average and chunks of <V of="tradeoff.sizes.chunk" fmt="num" />.

<span id="cx-fifty" />

Fifty questions, a minute apart, about a set of a million tokens, at Claude Sonnet 4.6's list prices:

- **The whole set in every prompt** costs <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long.cost.0" fmt="usd" /> a question, <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long.cum.49" fmt="usd" /> for the fifty, and with this simple latency model the first token arrives after <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long.ttft.0" fmt="s" /> of prefill, every time.
- **With the prompt cache**, the first call writes the set to the cache at a premium (<V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long+cache.cost.0" fmt="usd" />) and every later call reads it at the cache-read price, a tenth of the input price on Sonnet 4.6 (<V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long+cache.cost.1" fmt="usd" />): <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long+cache.cum.49" fmt="usd" /> for the fifty, <V of="derived.tradeoff.long_over_cache" fmt="num" /> times cheaper, and the later first tokens arrive in <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.long+cache.ttft.1" fmt="s" />. The cache pays for itself from the second question, as long as the questions come within its lifetime.
- **Retrieval** of the top five reranked chunks costs <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.rag.cost.0" fmt="usd" /> a question, <V of="tradeoff.runs.claude-sonnet-4.6|1000000|5.strategies.rag.cum.49" fmt="usd" /> for the fifty: another <V of="derived.tradeoff.cache_over_rag" fmt="num" /> times less than the cached long prompt, and its cost does not depend on the size of the set at all.

<span id="cx-give-up" />

What does retrieval give up? On this corpus, the answer is in the top five chunks for <V of="tradeoff.recall.5" fmt="pct1" /> of the questions (top three: <V of="tradeoff.recall.3" fmt="pct1" />; measured in [chapter 4](/learn/04-hybrid-and-reranking)). The long prompt always contains the answer, but containing it is not the same as using it: [chapter 6](/learn/06-packing-the-window) showed why an answer buried in the middle of a long input is used less often. The long prompt wins when questions need many scattered parts of the set at once, or when the set is small: at the corpus's own size (<V of="tradeoff.sizes.corpus" fmt="int" /> tokens) the cached long prompt costs <V of="tradeoff.runs.claude-sonnet-4.6|37499|5.strategies.long+cache.cum.49" fmt="usd" /> for the fifty questions, and retrieval's machinery may not be worth building.

</Layer>

Sets larger than the corpus are **hypothetical**: the same arithmetic for a bigger set. Latency uses the round-number hosted profile (prefill 5,000 tokens/s, a 400 ms overhead) and treats cached tokens as free to prefill. The cache rule is the engine's simple prefix model. Output is 50 tokens a question.

<Layer kind="maths">

<span id="cx-tradeoff-maths" />

Per question, the long prompt costs $(N + q)\,p_{\text{in}}$ and retrieval $(k \bar c + q)\,p_{\text{in}}$, so their ratio is about $N / (k \bar c)$: here $10^6 / (5 \times 180) \approx 1{,}100$ before output tokens. Caching divides the long prompt's per-question cost by $p_{\text{in}} / p_{\text{read}} = 1/\rho$ (10 at these list prices; 20 on Claude Sonnet 5.5, whose reads cost $\rho = 0.05$ of the input price) after a first call that costs $p_{\text{write}} / p_{\text{in}} = w$ times more (1.25 for the Claude models; GPT-5 mini charges no write premium). The cache's three numbers, $\rho$, $w$ and the minimum cacheable length, and today's values for each model, are derived once in [Agent Harnesses Explained, prompt caching](https://agent-harnesses-explained.vercel.app/learn/04-prompt-caching). The cached long prompt overtakes the uncached one at the second question, and never overtakes retrieval while $N\,p_{\text{read}} > k \bar c\,p_{\text{in}}$, that is while the set is more than $k \bar c \,p_{\text{in}}/p_{\text{read}} = k \bar c / \rho \approx 9{,}000$ tokens (twice that at $\rho = 0.05$).

Time to first token is the overhead plus the uncached prompt over the prefill rate: $N / 5{,}000$ seconds for an uncached million-token prompt.

</Layer>

<Remember>

- The long prompt pays for the whole set on every question; the cache makes later reads cost ρ of the input price.
- Retrieval's cost does not depend on the size of the set at all.
- Containing the answer is not using it: an answer in the middle of a long input is used less often.
- The long prompt wins when the set is small or a question needs many scattered parts of it at once.
